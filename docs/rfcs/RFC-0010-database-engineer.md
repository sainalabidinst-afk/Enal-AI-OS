## Motivation

Code Engineer generates database schemas and migrations. DevOps Assistant generates database deployment configs. Data Engineer generates ETL pipelines that read from and write to databases. However, none of these packs provide enterprise-grade database engineering expertise.

The Database Engineer Capability Pack provides a unified, expert-level layer for:

1. **Schema Design** — Optimal schema design for relational and NoSQL databases.
2. **Query Optimization** — Identify and remediate slow queries, deadlocks, and performance bottlenecks.
3. **Migration Management** — Safe, rollback-ready migration generation and validation.
4. **Replication & HA** — Recommend replication topologies and high-availability strategies.
5. **Backup & Restore** — Generate and validate backup/restore procedures.
6. **Index Recommendations** — Recommend indexes based on query patterns and data access.
7. **Performance Analysis** — Diagnose and resolve database performance issues.

Without Database Engineer, database-related artifacts generated by Code Engineer and DevOps Assistant lack the depth of expert DBA knowledge, leading to performance, reliability, and scalability issues in production.

---

## Problem Statement

Without a dedicated Database Engineer Capability Pack:

- **Schema design is basic** — Code Engineer generates schemas but does not apply normalization, indexing, or partitioning best practices.
- **Slow queries are not diagnosed** — No systematic analysis of query performance, execution plans, or bottlenecks.
- **Deadlocks are not predicted** — Concurrent access patterns that lead to deadlocks are not analyzed.
- **Migrations are not validated** — Generated migrations lack rollback safety, performance checks, and data validation.
- **Replication strategies are undefined** — No guidance on read replicas, sharding, or failover patterns.
- **Backup/restore procedures are incomplete** — No standard backup strategy generation or restore validation.
- **Index recommendations are missing** — No guidance on which indexes to create, which to drop, or how to maintain them.
- **Performance regressions go undetected** — Schema and migration changes are not benchmarked against performance baselines.

The absence of Database Engineer means database-related decisions are made without expert DBA knowledge, risking production stability and performance.

## Goals

1. **Schema Design** — Generate optimal schemas for relational (PostgreSQL, MySQL) and NoSQL (MongoDB) databases.
2. **Query Optimization** — Identify slow queries, analyze execution plans, and recommend optimizations.
3. **Migration Management** — Generate safe migrations with rollback plans, performance validation, and data checks.
4. **Replication & HA** — Recommend replication topologies and high-availability configurations.
5. **Backup & Restore** — Generate and validate backup/restore procedures.
6. **Index Recommendations** — Recommend indexes based on query patterns and access frequency.
7. **Performance Analysis** — Diagnose bottlenecks, analyze resource usage, and provide remediation.

### Success Criteria

| Metric | Target | Grade |
|--------|--------|-------|
| Query Optimization Accuracy | ≥90% (slow queries correctly identified and fixed) | A |
| Migration Safety | ≥95% (migrations are rollback-safe and validated) | A |
| Schema Quality | ≥85% (schemas meet best-practice standards) | A- |
| Index Recommendation Correctness | ≥90% (recommended indexes improve query performance) | A |
| Deadlock Detection | ≥90% (deadlocks correctly identified from access patterns) | A |
| Backup Strategy Quality | ≥95% (backup procedures are complete and validated) | A |
| Consistency | ≥90% (same schema/query produces same analysis across runs) | A |

---

## Non-Goals

1. **Live database administration** — Database Engineer analyzes and recommends; it does not directly connect to or modify production databases.
2. **Replacing Code Engineer's schema generation** — Code Engineer produces initial schemas; Database Engineer audits and optimizes them.
3. **Database-as-a-Service provisioning** — Provision of cloud databases is handled by DevOps Assistant.
4. **Real-time monitoring** — Continuous monitoring of database performance is out of scope (observability is DevOps' domain).
5. **Core modification** — All implementation resides within the Database Engineer Capability Pack.

## Capability Scope

### Core Capabilities

| Capability | Description | Inputs | Outputs |
|-----------|-------------|--------|---------|
| Schema Design | Generate optimal schemas for relational and NoSQL databases. | Requirements, entity definitions, access patterns | Schema DDL, indexing strategy, partitioning plan |
| Query Optimization | Identify and fix slow queries. | SQL queries, execution plans, database logs | Optimized queries, plan analysis, performance recommendations |
| Migration Management | Generate safe, rollback-ready migrations. | Schema changes, database state, constraints | Migration script, rollback script, validation checks |
| Replication & HA | Recommend replication topologies and HA strategies. | Scale requirements, RTO/RPO, budget | Replication topology, HA architecture, failover plan |
| Backup & Restore | Generate and validate backup/restore procedures. | Database size, RTO/RPO, storage | Backup strategy, restore procedure, validation checklist |
| Index Recommendations | Recommend indexes based on query patterns. | Queries, access frequency, data distribution | Index creation/drop recommendations, maintenance plan |
| Performance Analysis | Diagnose bottlenecks and resource issues. | Database metrics, query logs, system resources | Performance report, bottleneck analysis, remediation plan |

### Out of Scope

- Live database administration or direct database connection
- Cloud database service provisioning (DevOps domain)
- Real-time performance monitoring and alerting
- Data modeling for application logic (Code Engineer domain)
- Database security auditing (Security Engineer domain)


```
    │

    │

    │
```

## Benchmark Specification

### Benchmark Framework

| Dimension | Definition | Measurement | Target |
|-----------|------------|-------------|--------|
| **Query Optimization Accuracy** | Correct identification and optimization of slow queries | % of slow queries correctly identified and optimized | ≥90% |
| **Migration Safety** | Migrations are rollback-safe and validated | % of migrations passing safety, rollback, and validation checks | ≥95% |
| **Schema Quality** | Adherence to database design best practices | % of schema designs meeting best-practice standards | ≥85% |
| **Index Efficiency** | Recommended indexes improve query performance | % of index recommendations that improve query time by ≥20% | ≥90% |
| **Deadlock Detection** | Deadlocks correctly identified from access patterns | % of deadlock-prone patterns detected | ≥90% |
| **Backup Completeness** | Backup procedures cover all data and are restorable | % of backup plans passing completeness checklist | ≥95% |
| **Efficiency** | Analysis time for standard schema/queries | Latency P95 < 3000ms for schemas ≤100 tables | within budget |
| **Consistency** | Same input produces same output across runs | Variance across 5 repeated runs < 3% | ≥90% |

### Benchmark Dataset

- **100 database projects** covering:
  - PostgreSQL (40), MySQL (25), MongoDB (20), SQLite (15)

  - Deadlock scenarios (lock ordering, long transactions, concurrent writes)
  - Migration scenarios (column add/drop, type change, data transformation)
  - Index recommendation scenarios (read-heavy, write-heavy, mixed workloads)
  - Backup/restore scenarios (full, incremental, point-in-time recovery)

## ADR Impact

**Does this require Core changes?** No.

Database Engineer is a **new Capability Pack** that follows established patterns:

- **ADR-001 (Core Pipeline Freeze):** No Core changes. All logic in `apps/database_engineer/`.
- **ADR-002 (Capability Pack Independence):** Communicates with other packs via Execution Runtime tasks and shared contracts only.
- **ADR-003 (Worker = Adapter Only):** Thin Worker routes database tasks to the Domain Engine.
- **ADR-004 (Domain Engine Owns Business Logic):** All database engineering logic in `apps/database_engineer/engine.py`.
- **ADR-005 (Human Approval Required):** Migration execution and configuration changes require explicit user approval.
- **ADR-006 (Capability Contract v1 Frozen):** Uses existing Capability Contract for registration.
- **ADR-007 (Conversation Boundary):** Invoked through Execution Runtime.
- **ADR-008 (Core Change Requires Cross-Capability Proof):** Not applicable — no Core changes.
- **ADR-009 (Single Conversation Interface):** Users say "Optimize my database queries" — internal DB engine selection is transparent.
- **ADR-010 (Workspace Isolation):** Database findings and migration scripts scoped per Workspace.
- **ADR-011 (Artifact Persistence):** Migration scripts and analysis reports persisted as versioned Artifacts.
- **ADR-012 (Progress Transparency):** Progress shown as "Analyzing schema...", "Optimizing queries...", "Generating migration..."
- **ADR-013 (Outcome First Rule):** Users request outcomes ("Find slow queries"), not mechanisms.
- **ADR-014 (Operational Product Layer):** Uses Artifact Service for versioned migration script storage.

**ADR Required:** None. This is a new Capability Pack, not a Core modification.
